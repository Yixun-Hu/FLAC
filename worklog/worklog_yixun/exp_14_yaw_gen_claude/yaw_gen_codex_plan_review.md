VERDICT: REVISE

1. **BLOCKING — §§3.2–3.3, 5.2, 5.6: cross-arm rotation matching is not yet proven.** The drawing scheme is implementable and statistically reasonable: `shuffle=False` gives sequential indexing, and chunked draws from a dedicated CPU generator can be batch-size independent. However, an offset-only hash proves only the RNG sequence—not which sample received each offset. `SampleDataset.__getitem__` can recursively substitute another item after load/silence failures, while `AR_md.py` randomly selects context sources. Fix: pin batch size 64 and worker count 4; assert 6,337 items and expected `idx/path` at every stream position; record a canonical hash over ordered `(target idx/path, context-selection fingerprint, img_w, offset)` tuples in R and the corresponding input hash in Z. Require equality across arms and between paired Z/R cells. Also test that the dedicated generator does not advance global RNG state.

2. **BLOCKING — §§3.1, 4 "Validity gates," 6: the reference design is right, but the gates are not operationally defined.** Re-running every Z cell at the campaign pin is the correct paired reference; exp_11 rows should remain external checks. But "within seed-noise," "at the Z-cell floor," "clear degradation," and "~2σ" are not executable criteria. Same-seed 90°/Z comparisons are paired, so ordinary seed noise is not the appropriate tolerance, and a conditioning-level D3 residual does not directly define a metric tolerance. Pre-register numerical pass/fail tolerances and the exact scale used. Add a random-mode integration gate that checks a golden seed-42 assignment actually reaches `rotate_scene_metadata`. C4L@45 may legitimately be robust and therefore is not a guaranteed harness positive control; keep it as a mechanism control and add VANL@90 as the prior-supported empirical positive control. Update the grid count accordingly.

3. **BLOCKING — §4: the inferential specification is incomplete, and H3 uses data-dependent contrasts.** State explicitly that all estimates use five seed-paired observations, 95% paired-t CIs with `df=4`, and define `|Δ|` as the absolute per-seed aggregate-metric change. Pre-register metric directions and exact success rules. A clean convention matching exp_11 would be: Holm over the two co-primary endpoint tests within each H1/H2/H3; fixed arm-order adjacent contrasts reported with unadjusted descriptive CIs and no categorical verdict. "Adjacent pairs in the observed ranking" is selected using the same data and does not support ordinary confirmatory CIs; use the fixed order `VANL→C4L→C8→C16→C32`, while reporting the observed ranking descriptively.

4. **BLOCKING — §§5.2–5.3 and 8: the claimed fixed-mode byte compatibility contradicts the implementation plan.** Section 5.2 adds rotation keys to both record schemas, §5.3 acknowledges that fixed records acquire new keys, while §8 says fixed records remain byte-compatible. Preserve the current fixed-mode metrics record and prediction metadata exactly; add random provenance conditionally only in random mode. Tests must snapshot default/no-new-flag versus explicit fixed behavior for vanilla and FA, at zero and nonzero rotation: output paths, record keys/order and serialized JSON, prediction metadata, rotation dispatch, and global RNG behavior. Run the existing eval/yaw regression suite as well. Explicit `--rotate-seed` in fixed mode should error rather than be silently ignored.

5. **BLOCKING — §§5.2, 5.4: random artifact naming and sidecar ownership are ambiguous.** `_rotrand` is not injective across different rotation seeds when callers reuse an eval name; this recreates the overwrite class that `build_output_paths` was designed to prevent. Include the resolved rotation seed in the suffix, and test seed-42 versus seed-43 paths with the same eval name. Also, prediction metadata is created only under `--store_predictions`, which the plan forbids for this campaign. Specify that random hashes live in the metrics JSON and inherited `.screenmeta.json`; prediction metadata is updated only for future callers that actually store predictions. Define the canonical hash serialization and expected offset count.

6. **BLOCKING — §5.5: existence-only dedup is fail-open.** A stale, corrupt, partial, or wrong-pin metrics JSON would be silently skipped. Dedup only when the exact cell validates completely against checkpoint hash, campaign SHA, config/protocol, sidecar, sample count, and assignment hashes. If an artifact exists but fails validation, stop for triage rather than skipping or overwriting it. Pending/running cells should be recognized from manifests/leases separately.

7. **BLOCKING — §5.7 and announcement 04: the proposed VANL table update cannot work as written.** The current generator expects `exp11_VANL_q9...` files and treats Q9 as a four-cell same-pin transaction with C4L; its validator accepts exp_11 Q9 naming/contracts, not exp_14 Z names. Revise the implementation inventory to include an explicit exp_14 table contract and tests, then either migrate both VANL+C4L row specs to the exp_14 Z pin or add clearly labeled exp_14 rows. Regenerate, commit, and push immediately when the eligible two-K five-seed transaction completes—not only in a generic post-results phase.

8. **BLOCKING — §§5.4–5.6: the plan does not satisfy the per-function TDD directive for the collector and orchestration code.** "Pure aggregation functions tested with synthetic fixtures" is not the required per-function test list. Enumerate the intended functions and red tests for parsing, provenance validation, expected cell-set generation, assignment matching, seed pairing, paired-t CIs, Holm adjustment, metric direction, missing/duplicate seeds, validity-gate suppression, and PENDING rendering. Guardtests should assert the exact allowed V tuples and the complete unique grid, rejecting every unregistered arm/angle/cell combination.

9. **NIT — §3.1: in-group draws are not "contamination," and 6.25% is material.** For C32 this is about 396 of 6,337 samples per seed. It is legitimate support mass under the common uniform-yaw estimand and must not be removed arm-by-arm; describe it that way and disclose its contribution to expected flatness.

10. **NIT — §7: GPU-hour arithmetic is plausible, but the wall-clock claim needs qualification.** Given the quoted 13–36 minute cells, roughly 30–45 GPU-hours is credible. Four to six hours assumes prompt access to close to 16 L40 slots and should be labeled queue-excluded service time. The quoted Slurm durations, checkpoint availability, and 1.6-TB headroom were not independently remeasured here.
