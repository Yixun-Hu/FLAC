## 3. Answers to A–G

**A. Is the 67,500-step budget sound?** Yes, and it is better-supported than the plan claims — but it is a floor, not a proven endpoint. I re-verified `torch.load('weights/FLAC/FLAC.ckpt', map_location='cpu')`: `epoch=14`, `global_step=67500`, `optimizer_states[0].state[0]['step']=tensor(67500.)`, `lr_schedulers[0] = {inv_gamma:1e6, power:0.5, warmup:0.99, base_lrs:[5e-05], last_epoch:67500, _last_lr:[4.839339184958273e-05]}`, and `fit_loop.epoch_loop.batch_progress.current.processed=3800`. That last number is the plan's missing corroboration: 67500−3800 = 63700 = 14 × (291210//64 = 4550), so the epoch counter is only consistent with **global batch 64** — and the run stopped mid-epoch, not at an epoch boundary. The overclaim is "the budget": the callback key records `every_n_train_steps: 2500` and 67500 = 27×2500, so this file is a periodic snapshot; adopt it as the pre-registered budget (correct choice) while disclosing "≥ 67,500". The irreproducibility list (seed, worker scheduling, kernel nondeterminism) is otherwise adequate but should gain flash-attn (N12) and validation-RNG/val-set (N13).

**B. Recipe mapping paper→flags.** Batch 64 on one GPU is right and is now *evidenced*, not just asserted (A); README's 32×2 example gives the same global batch but the release's own run-directory name is `…_dinoViTS16FT_BS64`, so keep single-GPU. `precision = "bf16-mixed"` (`defaults.ini`) matches the paper's BF16; `--max-steps` exists (`train.py:78`, ini `max_steps`); `use_ema: true` (`FLAC_AR.json:137`) with `EMA(beta=0.9999, power=3/4, update_every=1, update_after_step=1)` at `src/training/diffusion.py:225-232`. The schedule: with `(1-0.99^(t+1))·5e-5·(1+t/1e6)^-0.5` (`src/training/utils.py:56-60`, stepped per optimizer step via `interval: "step"`, `src/training/diffusion.py:343`) I compute lr(67500) = **4.839339184958273e-05**, bit-identical to the checkpoint's `_last_lr` — warmup crosses 0.99 at step 458, and the inverse decay only removes 3.2% of the base LR over the whole run, i.e. it is effectively a constant-LR recipe; stopping at 67,500 is fully consistent with the release. Silently inherited defaults to state in `_params_set_up.md`: `gradient_clip_val = 0.0` (unknowable for the release — the checkpoint stores no Trainer hparams), `num_sanity_val_steps=0`, `log_every_n_steps=100`, `save_top_k=-1`, `accum_batches=1`, and `checkpoint_every 2500` — which the checkpoint now *confirms* the release used.

**C. `resolve_vit_model_path`.** The resolution order (existing dir → `<root>/<basename>` → unchanged) is correct and its shadowing risk is acceptable *for a hub id* but must be made observable: today's design would log the unresolved id (N2), so a wrong snapshot under `models/` would be untraceable in the run log. Portability is genuinely a no-op elsewhere only because `models/` won't exist there — but the `local_root="models"` default is CWD-relative, which is the weak spot (N1). The proposed 5 tests do **not** pin the call site as claimed: with `from_scratch:false` only `AutoModel.from_pretrained` (`src/models/conditioners.py:458`) executes; `AutoConfig.from_pretrained` (line 455) is on the `from_scratch:true` branch (N3). Keeping the JSONs byte-unchanged is the right call — `ModelConfigEmbedderCallback` (`train.py:16-21`) bakes the config into every checkpoint, so a della-edited path would propagate into the reproduction artifact and into any downstream comparison; the hub id keeps the ckpt portable. But note B2/B3: the AGREE side needs the same treatment, and populating the HF cache would make the whole code change optional.

**D. Phase-1 calibration.** Run B against exp_01's stored seed-42 JSON is a sound anchor and is unusually clean here: same torch 2.7.0 / PL 2.1.0 / transformers 4.57.0 pins, same math-attention fallback (no flash-attn on either side), same `--batch-size 64 --num-workers 4` defaults, same `shuffle=False` sequential sampler — so the only real deltas are Ampere→Hopper kernels and TF32 selection under `torch.set_float32_matmul_precision('medium')` (`eval_FLAC.py:819`). Dropping `--store_predictions` is acceptable and correctly justified — `build_output_paths` (`eval_FLAC.py:179-187`) writes the `.pt` next to the checkpoint, which would put ~GB of decoded audio in `$HOME` — and it does not affect the metrics path. The announcement-05 flag set (`--cond-method vanilla --cond-autocast default --seed 42`) is complete for a vanilla checkpoint; `--rotate-deg` may be omitted (default 0.0) but should still be *written down* in the params file, since announcement 05 asks for the protocol to be stated, not merely defaulted. The band definition needs fixing per B7, and two seeds would make the anchor much more informative (N10).

**E. Phase-2 run design.** The ladder's shape is right; the smoke is mis-specified for its stated purpose (N5) and the QOS decision rule is optimistic (N7). The BN/EMA claim **is correct and I verified the mechanism**: EMA updates only in `on_before_zero_grad` (`src/training/diffusion.py:621-623`), which PL calls only in the training loop; PL puts the LightningModule in `eval()` for the validation loop, so the RIR encoder's BatchNorm (via `AudioResNet18`, `src/models/conditioners.py:152`) does not update running stats; and the one line that re-enters train mode inside `validation_step` — `self.diffusion.pretransform.train(self.diffusion.pretransform.enable_grad)` (`src/training/diffusion.py:648`) — is a no-op because `AutoencoderPretransform` is constructed with `enable_grad=False` (`src/models/pretransforms.py:31`). What validation *does* perturb is the global RNG stream (N13). Checkpoint math checks out: 27 × ~724 MB ≈ 19.5 GB, against 7.0 TB free on `/scratch/gpfs`; and because 67,500 is a multiple of 2,500 the final save lands exactly at `epoch=14-step=67500.ckpt`, which `eval_FLAC.py` can consume directly — its whitelist `("diffusion_ema.", "losses.")` (`eval_FLAC.py:734`) makes the wrapped checkpoint load cleanly, so no `unwrap_model.py` step is needed. Slurm facts in the worklog check out (`gpu-short` 1 d / `gpu-medium` 3 d / `gpu-long` 6 d; `gpu:h100:4|8` and `gpu:h200:8` GRES present); what the sbatch section is missing is `--cpus-per-task` / `--mem` / `--time` (N5) and the import/interpreter gates (B1, N4).

**F. Phase-3 bands.** ±10%/±20% is simultaneously far too loose for the eval-noise-dominated metrics and too tight for the training-variance-dominated ones — exp_01's 5-seed floors are T60 ±0.012 (0.14%), C50 ±0.003 (0.31%), EDT ±0.07 (0.19%), R@1 ±0.10 (1.4%) at K=8, so ±10% is 70σ on T60 and ±20% would pass a catastrophic regression; meanwhile prior from-scratch runs miss the release's R@1 by 9.5–13.5% (B4). Suggested pre-registration: **C50 ±3%, T60 ±8%, EDT ±8%, FD ±5%, R@1/R@5/R@10 ±20%** at both K, all judged against the release *and* reported side-by-side with `P1 vanilla @67.5k`; plus two structural criteria that n=1 can actually support — K=8 must beat K=1 on T60/C50/EDT, and every metric must be at least as good as the worst prior full-budget from-scratch run. And the honest framing: with n=1 the experiment establishes *pipeline validity* (Phase-1 anchor + healthy loss curve + endpoint in the prior-run envelope), not a reproduction hypothesis test; the verdict language should say so.

**G. SOP compliance.** Structure is good — scaffold/query/worklog present, plan before code, per-round reviews plus a `full` integrative review before the launch, six sub-200-line commits, its own branch, no edits to the exp_11/14/15 kits, `git pull --rebase` noted. Gaps: (i) the TDD rung is unrunnable until pytest is installed, and the plan never says so (B1); (ii) the sbatch kit is tested only by `bash -n` + `DRYRUN` while exp_11/14 precedent has real pytest coverage for their runners (`src/tests/test_exp11_p0_runner.py`, `test_exp14_validate_cell.py`) — defensible for a single-writer kit, but say it is a deliberate scope call; (iii) storage discipline is right in spirit but leaves the announcement-04 path broken (N8); (iv) two-writer safety has one concrete hole, the un-ignored `AcousticRooms` symlink (B6), and one soft one — commit 2 touches `.gitignore`, a file the other session also edits, so rebase before that commit specifically; (v) announcement 01 is satisfied throughout (full seen/unseen configs, K switched only by existing config files).

## 4. Overall assessment

This is a well-constructed plan whose central scientific move — recovering the unstated training length from the released checkpoint and pre-registering it — is not only sound but better supported than the plan realizes: the loop state, the LR-scheduler state (which I reproduced to the last digit), the 2500-step callback cadence, and the run directory literally named `…BS64` all corroborate a single-GPU batch-64 run of ≥67,500 steps, and the epoch-14 arithmetic is an independent batch-size witness once the split is counted correctly (291,210 items → 4,550 steps/epoch, not 288k → 4,500). What blocks approval is not the method but the pre-flight: **the della environment cannot import this codebase today** (`pkg_resources` gone from setuptools 83), **the advertised HF-cache fallback is an empty 94 KB stub**, and **the AGREE metric model performs a second, un-patched hub-id fetch**, so all three of Phase 1's runs would fail before touching a metric — and the plan's ladder, which begins at `py_compile`, is structured such that a Slurm allocation is what discovers this. Alongside that, two pre-registrations need repair before they bind: the Phase-1 gate has an FD band roughly 10× tighter than plausible cross-architecture drift and one threshold deferred to analysis time, and the Phase-3 ±10% rule would grade all three of this repo's own prior full-budget vanilla reruns as failures. Fix B1–B7, fold in N1–N6, and this becomes a tight, well-instrumented experiment whose main remaining risk is throughput — which the smoke, once it is long enough to include a validation pass, will settle.
