**BLOCKING findings**

1. Both mutual-exclusion checks fail open when `squeue` fails. The submit wrapper converts any scheduler-query failure into an empty `EXISTING`, while the leg pipeline similarly uses `|| true`, conflating “only self/no matches” with controller, authentication, or argument failure. A chain can therefore be submitted—or enter `train.py`—without proving that no racer is writing the production save-dir. Capture `squeue` output first and make a nonzero status fatal for real submissions/legs; then perform self-filtering with a command that returns zero on an empty result. (`della_chain_submit.sh:148-159`; `della_chain.sbatch:240-249`)

**NON-BLOCKING findings**

1. The arithmetic is internally correct: S=67500 takes CHAINDONE; S=60000 produces LEG=8, SEED=50, TARGET=67500; S=62500 also produces LEG=8, SEED=50, TARGET=67500. The latter replays the same permutation head already consumed before the crash because PL restarts the loader. This is disclosed-acceptable rather than blocking—the failure path is rare, same-S retries remain deterministic, and it matches Rev 4—but checkpoint-indexed reseeding is strictly cleaner. Prefer `SEED=$((42 + S / CHECKPOINT_EVERY))`; unlike hard-coded `S/2500`, that also preserves probe seeds 42/43/44. (`della_chain.sbatch:272-275`, `della_chain.sbatch:304-328`; `plan_della_vanilla_repro.md:168-176`)

2. A normally invoked new submission cannot overwrite an active chain’s manifest because any existing chain/racer job is checked before the manifest is touched. Moreover, manifest membership is verified before every `cancel_later` path: an old leg reading a new manifest exits rc=12 rather than cancelling new IDs; a leg that cached its old manifest cancels only old later IDs. There remains a concurrent-wrapper TOCTOU: two invocations can both pass the queue check before either submits, and the record lock covers only the final write—not check→submit→release; a failing invocation can also remove the other’s shared manifest. This risks supersession/GATEFAIL, not innocent-job cancellation. A transaction-wide submission lock or chain-specific manifest exported by first-job ID would close it. (`della_chain_submit.sh:148-159`, `della_chain_submit.sh:213-285`; `della_chain.sbatch:144-180`, `della_chain.sbatch:252-290`)

3. Cadence progress correctly resets the watchdog logically: if a timed-out leg saves step 62500/65000, the successor discovers that new S, so the old stamp key no longer increments. However, the stamp’s read-modify-write is not genuinely flock-serialized: it is read outside the lock, and `200>"$STAMP"` truncates before `flock` acquires the lock. Afterany normally prevents overlap, so this is non-blocking; a separate lockfile with read/check/write all inside the locked region would be correct. Also, CHAINHALT is detected by the third job observing two starts at the same S; if the final required leg and spare both fail without progress, the chain simply exhausts without emitting CHAINHALT. (`della_chain.sbatch:277-302`, `della_chain.sbatch:351-364`)

4. Probe parameters are correct: 300/100 yields three working legs plus one spare, checkpoint refusal is enforced, and `--val-every -1` cannot reach epoch-end validation within 100 steps. On the happy path, however, leg 3 logs CHAINDONE after reaching 300 and cancels leg 4, so the spare does not itself exercise the entry-time CHAINDONE branch. If that branch is an explicit probe acceptance criterion, it needs a separate invocation/test; operational behavior is otherwise clean. (`della_chain_submit.sh:117-120`, `della_chain_submit.sh:161-173`, `della_chain_submit.sh:187-194`; `della_chain.sbatch:200-208`, `della_chain.sbatch:265-269`, `della_chain.sbatch:365-370`)
